## Main unresolved Word failure and current investigation

Repeated ribbon changes sometimes leave Word unusable. The original problem
occurs in Office's background layout code, in `PrefetchAxis::Add`, while inserting
into a set of prefetch elements. The later message on the UI thread is Office's
reporting path, rather than the original problem.

The latest debugger observation is stronger than the earlier general suspicion:

- The same `PrefetchScope` object is used across successive layout operations.
- Its pending-notification member normally points to a temporary set on the
  current layout stack.
- Just before a failing insertion, that member instead contains text-like data.
- The entry's owner points to the current scope's expected member. This is not
  simply an entry referencing some unrelated scope.
- Other captured failures find a null set head instead of a valid set.

The exact writer and cause remain unproven. A plausible next diagnostic is to
watch writes to that member and record thread/order information. Concurrent
scope updates could restore an old member value while another update is active,
but this is a hypothesis, not a finding. Do not implement a timing delay or
Office-specific suppression based on it.

Useful source-level detail from the Office symbols and disassembly: scope Update
saves the previous pending-notification member, puts a local set there, and
restores the previous value on exit. The constructor does not appear to initialize
that member. An old text-like value outside Update is therefore not sufficient
proof of corruption; the important observation is that it is read during an
active Update.

Completion behavior is also under investigation:

- `composition_scoped_batch_End` invokes handlers synchronously.
- `completed_action_put_Completed` invokes an already-completed action's handler
  synchronously.
- The candidate has disabled-by-default `uilifetime` logging for those paths.
- Office registers action completion in `CompositorWinCompWin32::TryCommitAndFireEvents`.
- Only one scoped-batch End was observed in one long tab run; many action
  completions occurred. Neither observation proves the cause.
- Earlier CommitNeeded diagnostics showed the Office handler was agile and
  invoked on its registering thread. Missing handler marshaling was not supported
  by that run.

Diagnostics in `windows.ui/composition.c` use channels `uievents` and
`uilifetime`. Staged DLLs include these diagnostics. They are not enabled by
default. The generic Wayland traces use `uistack`.
